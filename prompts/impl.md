# 단계: 구현

기능: $FEATURE

## 출력 (이 파일 하나만 쓴다 — 코드 변경은 별개)

$WORK/IMPL.md

## 입력 (읽기만, 절대 수정 금지)

- `$WORK/DESIGN.md` — 이 설계를 그대로 구현한다
- `$WORK/JUDGE.md` — 설계 주장에 대한 감사 결과. **`반박` 항목이 있으면 그 주장에
  기대는 구현을 하지 마라**. 설계가 그 위에 서 있으면 STATUS: BLOCKED
- `$WORK/FAIL_LOG.md` — 비어있지 않다면 이전 시도가 실패한 것이다. 같은 실패를 반복하지 마라

## 프로젝트 컨텍스트 (neemba)

- python: `services/python`. 테스트는 `.venv/bin/python -m pytest -q` (시스템 python 금지)
- node: `services/node`. 테스트는 `npm test` (vitest)
- 코드 주석은 주변 코드와 같은 밀도로. 이 저장소는 **"왜 이렇게 했나"** 를 남기는
  주석을 쓴다 — 함정·경계조건·과거에 겪은 버그. 자명한 것은 안 쓴다
- 파일을 새로 만들기 전에 **기존 모듈에 같은 역할이 있는지 먼저 본다**

## 할 일

1. DESIGN.md 의 "변경 대상 파일 목록"대로만 수정한다.
2. 목록에 없는 파일을 건드려야 한다면 STATUS: BLOCKED.
   이건 부탁이 아니다 — 구현 직후 셸이 `git status` 와 DESIGN.md 의 ALLOWED_FILES 를 대조해서
   목록 밖 파일이 하나라도 바뀌었으면 파이프라인을 죽인다. 우회로는 없다.
3. 작업 요약을 `$WORK/IMPL.md` 에 쓴다.

## IMPL.md 필수 섹션

- STATUS 라인 (첫 줄)
- 실제로 수정한 파일 목록 (설계와 다르면 그 이유)
- 설계와 달라진 점 (없으면 "없음")
- 다음 단계(검증)가 알아야 할 것 — 특히 **어떤 경계조건이 위험한지**

## 금지

- 테스트를 작성하지 않는다. 그건 다음 단계다.
- 설계를 바꾸지 않는다. 설계가 틀렸으면 BLOCKED.
- **`$WORK/DESIGN.md`·`$WORK/JUDGE.md` 를 수정하지 않는다.** 읽기 전용 입력이다.
- 기존 테스트를 통과시키려고 **테스트 쪽을 고치지 않는다.** 구현이 틀린 것이다.
