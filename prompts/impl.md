# 단계: 구현

기능: $FEATURE

## 출력 (이 파일 하나만 쓴다)
$WORK/IMPL.md

## 입력 (읽기만, 절대 수정 금지)
- `$WORK/DESIGN.md` — 이 설계를 그대로 구현한다
- `$WORK/JUDGE.md` — 설계 주장의 감사 결과. **`반박` 판정이 있으면 그 주장에 기댄
  부분을 그대로 구현하지 마라** — 사실이 아닌 전제 위에 코드를 얹는 것이다. `STATUS: BLOCKED`
- `$WORK/VERIFY.md` — 검증 단계가 **구현 전에** 쓴 테스트의 목록·인터페이스·지금의 실패 내용.
  이 테스트들이 통과하게 만드는 것이 네 일이다. 셸이 구현 전에 이 테스트가 실패하는 것(red)을
  이미 확인했고, 네가 끝나면 같은 명령이 통과하는지(green) 확인한다
- `$WORK/FAIL_LOG.md` — 비어있지 않다면 이전 시도가 실패한 것이다. 첫 줄에 어느 명령이
  실패했는지 있다. 같은 실패를 반복하지 마라

## 프로젝트 컨텍스트 (neemba)

- python: `services/python`. 테스트는 `.venv/bin/python -m pytest -q` (시스템 python 금지)
- node: `services/node`. 테스트는 `npm test` (vitest), 타입 검사는 `npx tsc --noEmit` —
  셸은 이 셋을 전부 돌려 green 을 판정한다
- 코드 주석은 주변 코드와 같은 밀도로. 영어로 쓴다. 이 저장소는 **"왜 이렇게 했나"** 를 남기는
  주석을 쓴다 — 함정·경계조건·과거에 겪은 버그. 자명한 것은 안 쓴다
- 파일을 새로 만들기 전에 **기존 모듈에 같은 역할이 있는지 먼저 본다**

**읽기 범위**: DESIGN.md 의 `ALLOWED_FILES` 와 거기서 직접 참조하는 파일부터 읽어라.
저장소를 처음부터 탐색하지 마라 — 설계가 이미 그 일을 했다. 다만 **경계는 아니다**:
관례 확인(테스트 픽스처·설정 등)에 다른 파일이 필요하면 읽어라. BLOCKED 사유가 아니다.

## 할 일
1. DESIGN.md 의 "변경 대상 파일 목록"대로만 수정한다.
2. 목록에 없는 파일을 건드려야 한다면 `STATUS: BLOCKED`.
   이건 부탁이 아니다 — 구현 직후 셸이 `git status` 와 DESIGN.md 의 ALLOWED_FILES 를 대조해서
   목록 밖 파일이 하나라도 바뀌었으면 파이프라인을 죽인다. 우회로는 없다.
3. 허용된 검사 명령(테스트·린트)을 **실제로 돌려** VERIFY.md 의 테스트가 통과하는지 확인한다.
   거부되면 우회하지 않고 IMPL.md 에 "확인하지 못한 것"으로 적는다.
4. 작업 요약을 `$WORK/IMPL.md` 에 쓴다.

## 테스트가 설계와 어긋나면 — 고치지 말고 BLOCKED

테스트는 red 로 검증된 채 고정돼 있다. 너는 테스트를 한 글자도 못 고친다(아래 금지).
테스트가 설계와 모순되거나(설계는 A 를 반환하라는데 테스트는 B 를 기대), 설계에 없는
인터페이스를 부르면 **테스트에 맞춰 설계를 비틀지 말고** `STATUS: BLOCKED` 로 올려라.
BLOCKED_REASON 에 어긋난 테스트의 **파일:줄**과 설계의 해당 문장을 나란히 적는다 — 사람이
어느 쪽을 고칠지 정한다.

## IMPL.md 필수 섹션
- STATUS 라인 (첫 줄)
- 실제로 수정한 파일 목록 (설계와 다르면 그 이유)
- 설계와 달라진 점 (없으면 "없음")
- **실행해서 확인한 것 / 확인하지 못한 것** — 돌린 명령과 실제 출력만 쓴다.
  못 돌렸으면 그 이유를 쓴다. "될 것으로 보인다"는 금지
- VERIFY.md 의 테스트 중 통과시키지 못한 것과 그 이유 (없으면 "없음")

## 금지
- **테스트를 작성하지 않는다.** 그건 이미 끝난 앞 단계(검증)의 일이다.
- **테스트를 고치지 않는다.** 기존 테스트든 새 테스트든 깨지면 그건 구현이 뭔가를 깬 신호다.
  테스트를 고쳐서 통과시키는 것은 이 단계의 가장 나쁜 실패 모드다 — 막히면 위 BLOCKED 규칙을 따른다.
  부탁이 아니다: DESIGN.md 의 `TEST_FILES` 에 있는 파일은 셸이 이 단계 전후 지문으로 대조해
  한 글자라도 바뀌면 파이프라인을 죽인다.
- **설계를 바꾸지 않는다.** 설계가 틀렸으면 BLOCKED. DESIGN.md·JUDGE.md 는 셸이 지문으로
  감시한다 — 한 글자라도 바뀌면 파이프라인이 죽는다.
- **의존성을 추가하지 않는다.** 패키지 설치 명령을 돌리지 않는다. 필요하면 BLOCKED.
- 테스트 러너·린터·타입 검사 설정을 수정하거나 새로 만들지 않는다. 셸이 지문으로 감시한다.
- **"테스트가 통과할 것으로 보인다" 를 쓰지 않는다.** 판정은 셸이 한다.
