# 단계: 판단 검증

기능: $FEATURE

설계 문서의 **주장**을 감사한다. 설계를 고치는 단계가 아니고, 구현 품질을 보는
단계도 아니다. **"이 문서가 사실이라고 말한 것들이 실제로 사실인가"** 하나만 본다.

이 단계가 있는 이유: 구현물은 테스트·리뷰·게이트를 통과하는데 **판단물(원인 판정,
우선순위, "X가 없다")은 아무 검증 없이 다음 단계로 흘러간다.** 틀린 1순위는 틀린
코드보다 비싸다 — 며칠을 엉뚱한 곳에 쓰게 만든다.

## 출력 (이 파일 하나만 쓴다)
$WORK/JUDGE.md

## 입력 (읽기만, 절대 수정 금지)
- `$WORK/DESIGN.md` — 감사 대상
- `$ROOT/docs/handover-2026-08-02.md` — 결정 이력·지뢰·"반증된 것"(`docs/handover-archive.md` 에
  지난 스트림 기록). 설계가 거기 반증된 주장을 되살렸다면 그것만으로 `반박`이다

## 이 저장소에서 자주 나온 오류 (여기부터 의심할 것)

- **부재 주장을 한쪽만 보고 단정한다.** neemba 는 `services/node` 와
  `services/python` 두 스택이다. "로깅이 없다" 를 python 만 grep 하고 쓴 적이
  실제로 있다 — 원문 로그는 node 에 있었다. 부재 주장은 **양쪽 전수 확인**
- **목록에 뜨는 것과 쓸 수 있는 것을 혼동한다.** 외부 API 가 지원 목록에
  올려놓고 실제 호출은 `PERMISSION_DENIED` 를 내는 사례를 겪었다.
  "문서에 있다" 는 `추정` 이지 `실측` 이 아니다
- **줄번호가 자기 diff 때문에 어긋난다.** `파일:줄` 로 짚었으면 그 줄을 실제로
  열어 확인한다. 상수·함수 **이름으로 grep** 하는 편이 안전하다
- **테스트 결과를 인터프리터 탓으로 오독한다.** python 테스트는
  `.venv/bin/python -m pytest` 여야 한다. 시스템 python 은 수집 단계에서
  12건 에러가 나므로, 임포트 에러를 봤다면 코드가 아니라 인터프리터를 먼저 의심
- **측정되지 않은 것을 1순위에 올린다.** 우선순위 주장은 측정 여부를 함께 본다
- **prod 인프라는 확인 경로가 아니다.** 이 단계는 로컬 저장소 읽기·로컬 테스트만 한다.
  EC2·DB·NATS 에 붙어야 확인되는 주장은 `미확인` 으로 두고 "무엇을 실행하면 되는지"를 적는다

## 할 일

1. `$WORK/DESIGN.md` 에서 **하중을 받는 주장**을 전부 뽑는다. 하중을 받는다 =
   그게 틀리면 설계의 방향·순서·범위가 바뀐다.
   - 원인 판정 ("느린 이유는 N+1 쿼리다")
   - 우선순위·순서 근거 ("A 를 먼저 해야 한다")
   - 부재 주장 ("이 기능은 없다", "로깅이 없다", "테스트가 없다")
   - 현재 동작 주장 ("이 API 는 500 을 반환한다")
   - 비용·성능·보안 주장 (숫자를 동반하는 것)
   - 외부 스펙·라이브러리 동작 주장

   설계 취향(네이밍, 파일 배치)이나 아직 만들지 않은 것에 대한 계획은 대상이 아니다.

2. **★ 확인을 시작하기 전에 산출물을 먼저 한 번 써라.** `STATUS`·카운트·주장 표(판정은
   전부 `미확인` 으로 초기화)를 쓰고, 확인이 끝날 때마다 갱신한다. 예산이나 턴이 끊기면
   **마지막에 쓰려던 것은 통째로 사라진다** — 2026-08-24 확인을 다 마치고 Write 하는
   순간 예산이 끊겨 $5 를 쓰고 산출물이 0 이었다. 중간 저장본의 카운트는 항상 정직해야
   한다 — 아직 확인 안 한 것은 `미확인` 이다.

3. 각 주장에 **근거 등급**을 매긴다.
   - `실측` — 도구를 실제로 돌린 출력이 근거
   - `코드확인` — `파일:줄` 로 짚을 수 있음
   - `추정` — 위 둘이 아닌 전부 (관례·유추·문서만 읽음·그럴듯함)

4. **확인이 가능한 주장은 직접 확인한다.** 이게 이 단계의 본론이다.
   `$ROOT` 에서 grep/테스트/스크립트를 돌려 재현한다. 확인 비용이 도구 호출
   1~2회면 반드시 한다. 문서만 읽고 넘기지 않는다.
   - **DESIGN.md 가 `파일:줄` 을 적어둔 주장은 그 좌표로 직행한다.** 저장소를 다시
     탐색해서 같은 것을 찾아내지 마라 — 좌표가 틀렸으면 그 자체가 발견이다.
   - 부재 주장은 **전수 확인**한다. 서비스·언어가 여러 개면 전부 본다
     (한쪽만 grep 하고 "없다"고 한 것이 실제로 자주 나오는 오류다)
   - 숫자 주장은 산수를 해본다. 자릿수가 맞는지만 봐도 죽는 주장이 많다
   - **도구가 거부되면 우회하지 말고 즉시 `미확인` 으로 센다.** 이 단계는 보통 tty 없는
     백그라운드로 돈다 — 네트워크·임의 스크립트는 승인을 받을 수 없어 거부된다. 다른
     명령·다른 도구로 갈아타며 재시도하면 예산만 태우고 같은 곳에 도착한다(2026-08-24
     실측: 4회 왕복 끝에 예산 초과, 산출물 0). "무엇을 실행하면 확인되는지"를 적어
     사람에게 넘겨라 — 그게 이 단계가 할 일이다.
   - **외부 문서를 가져오지 않는다** (WebFetch·WebSearch). 주행마다 다른 답을 주고(재현성),
     길어서 예산이 먼저 닿는다. 표준 라이브러리·설치된 패키지의 동작은 로컬에서 한 줄
     실행으로 확인한다 — 그게 저장소 안의 정본이다. 저장소 안에 정본이 없는 외부 API
     표면은 `미확인` 으로 남긴다.

5. 확인 결과를 판정으로 적는다.
   - `확인` — 주장이 맞다 (재현 방법·출력 요약을 남긴다)
   - `반박` — 주장이 틀리다 (**무엇이 실제인지**와 근거를 남긴다)
   - `미확인` — 이 단계에서 확인 못 했다 (**왜** 못 했는지, 누가 무엇을 하면
     확인되는지 남긴다)

## JUDGE.md 필수 형식

첫 줄은 STATUS 라인. 그 다음 줄에 **기계가 읽는 카운트 한 줄**을 정확히 이 형식으로:

```
STATUS: DONE
UNVERIFIED: <미확인 개수> REFUTED: <반박 개수>
```

파이프라인 셸이 이 숫자를 파싱한다. **하나라도 0 이 아니면 사람 게이트가 뜬다**
(무인 실행이어도 멈춘다). 숫자를 낮게 쓰려고 판정을 무르게 하지 말 것 — 그건
이 단계를 무의미하게 만드는 유일한 방법이다. 애매하면 `미확인` 으로 센다.

이어서 주장별 표를 쓴다.

| # | 주장 (원문 인용) | 등급 | 판정 | 근거 / 실제 |
|---|---|---|---|---|

마지막에 다음 두 절을 반드시 쓴다.

- **구현 전에 해소해야 할 것** — `반박` 과, 방향을 바꿀 수 있는 `미확인`.
  각 항목에 "무엇을 하면 풀리는지" 를 적는다
- **그대로 진행해도 되는 것** — 틀려도 손해가 작은 `미확인`. 왜 작은지 한 줄

## 금지

- **설계 문서를 수정하지 않는다.** 틀린 게 있으면 JUDGE.md 에 적을 뿐이다
- **코드를 수정하지 않는다.** 확인을 위한 읽기·실행만 한다. 확인용 임시 파일을
  만들었으면 지운다 — 셸이 `git status` 로 대조한다
- 주장이 없는데 억지로 채우지 않는다. 하중받는 주장이 0 개면 그렇게 쓴다
- **"통과했습니다" 로 끝내지 않는다.** 확인하지 않은 것을 `확인` 으로 적는 것이
  이 단계의 유일한 실패 모드다. 확인 못 했으면 `미확인` 이 정답이다
- 설계 자체가 읽을 수 없거나 하중받는 주장을 판별할 수 없으면 `STATUS: BLOCKED`
