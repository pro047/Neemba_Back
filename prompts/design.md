# 단계: 설계

기능: $FEATURE

## 출력 (이 파일 하나만 쓴다)
$WORK/DESIGN.md

## 입력 (읽기만, 절대 수정 금지)
- `$ROOT` 의 관련 코드
- `$ROOT/docs/handover-2026-08-02.md` — **현행 핸드오프**. 현황·우선순위·지뢰가 여기 있다
- `$ROOT/docs/` 의 해당 계획 문서 — 있으면 **그것이 정본**이다. 설계를 새로 짜지 말고
  그 계획의 미완료분을 구현 가능한 형태로 내려 쓴다. 계획과 어긋나면 그 사실을 명시한다

## 프로젝트 컨텍스트 (neemba)

실시간 예배 통역 파이프라인이다. 요청/응답 API 가 아니라 **상시 스트림**이다.

```
node (STT·RTMP·마이크 업링크) → NATS → python (문장분리·DeepL·허브) → WS 청취자
```

- 셸의 검증 명령 (전부 통과해야 green — CI `ci.yml` 과 같다):
  - python `cd services/python && .venv/bin/python -m pytest -q`
  - node `cd services/node && npm test` (vitest)
  - node 타입 검사 `cd services/node && npx tsc --noEmit`
- **시스템 python 으로 돌리면 `prometheus_client`·`nats` 미설치로 수집 단계에서
  12건 에러가 난다** — 이걸 코드 결함으로 오독하지 말 것
- 메트릭은 python `src/monitoring/metrics.py`, node `prom-client` 기본 레지스트리.
  Prometheus·Grafana 는 **dev 전용**이다 (`docker-compose.prod.yml` 에 0건)
- 문서 규칙: 계획 문서가 정본이고 핸드오프는 현황 레이어만 갱신한다. 복제하지 않는다

## 할 일
1. 관련 코드와 위 문서를 읽고 현재 구조를 파악한다.
2. 이 기능의 설계를 `$WORK/DESIGN.md` 에 쓴다.

## DESIGN.md 필수 섹션
- STATUS 라인 (첫 줄)
- **근거 있는 현황 서술** — 아래 "근거 등급" 규칙을 따른다
- 변경 대상 파일 목록 (경로 명시, 신규/수정 표시)
- 공개 인터페이스 (함수 시그니처 / API 스펙 / 스키마 / 설정 파일 구조)
- 데이터 흐름 (입력 → 처리 → 출력)
- 검증 기준: 이 기능이 "됐다"는 걸 무엇으로 확인하는지 **테스트 케이스 수준으로**.
  **자동 테스트로 확인되는 것과 사람이 직접 돌려봐야 하는 것을 나눠서 쓴다** (아래 "검증 가능성")
- 하지 않는 것 (범위 밖 명시)
- `ALLOWED_FILES:` 블록과 `TEST_FILES:` 블록 (아래 형식 엄수 — 셸이 파싱한다)

## 근거 등급 — 주장마다 붙인다

다음 단계(판단 검증)가 이걸 감사하고, `반박`·`미확인` 이 0 이 아니면 파이프라인이 사람
게이트에서 멈춘다. 등급 없이 단정하면 전부 `추정`으로 취급된다. **모르는 것은 `추정` 으로
표시하는 편이 틀린 `확인` 보다 싸다.**

- **실측** — 도구를 실제로 돌린 출력이 근거. 명령과 출력 요약을 함께 적는다
- **코드확인** — `파일:줄` 로 짚을 수 있다. **경로와 줄번호를 반드시 본문에 적는다** —
  다음 단계가 이 좌표로 직행해서 확인한다. 좌표 없는 코드확인은 `추정` 으로 강등된다
- **추정** — 위 둘이 아닌 전부

셋을 섞어 한 문장에 담지 않는다. 확인 비용이 도구 호출 1~2회면 **확인하고 쓴다.**
**"X 가 없다" 는 부정 주장은 `services/node` 와 `services/python` 을 둘 다 본 뒤에만** 쓴다.
한쪽만 grep 하고 단정한 것이 이 저장소에서 실제로 여러 번 나온 오류다.
비용·성능 주장은 숫자 없이 하지 않는다.

## 검증 가능성 — 설계 단계에서 정해진다

검증 기준을 쓸 때 두 가지로 나눠라:
- **[테스트 가능]** — 셸이 위 검증 명령으로 돌려서 판정할 수 있는 것
- **[사람 확인 필요]** — 못 돌리는 것 (실제 STT·DeepL 호출, 실예배 타이밍, 청취자 화면 육안 확인)

**검증 가능한 쪽으로 구조를 밀어라.** 진입점·핸들러 안에 로직을 묻지 말고 순수 함수로
빼면 그만큼 [테스트 가능] 으로 넘어간다. 부작용(I/O·네트워크·시계)과 판정 로직의 분리가 그 축이다.

## ALLOWED_FILES 블록 (형식 엄수 — 셸이 파싱한다)

"변경 대상 파일 목록" 과 **별도로** 아래 블록을 정확히 이 모양으로 넣는다.
목록은 사람이 읽고 이 블록은 셸이 읽는다. 둘의 내용은 일치해야 한다.

ALLOWED_FILES:
- src/foo.ts
- test/foo.test.ts

규칙:
- 저장소 루트 기준 상대 경로. `./` 접두사 금지.
- 한 줄에 하나, `- ` 로 시작. 블록은 빈 줄로 끝난다. 주석·설명을 섞지 않는다.
- 구현이 새로 만들 파일, **검증 단계가 만들 테스트 파일까지 미리 다 넣는다.**
  여기 없는 파일이 변경되면 파이프라인이 그 자리에서 죽는다. 재시도가 아니라 종료다.
- **소스를 넣으면 짝이 되는 테스트 파일도 함께 넣는다** (`TEST_FILES` 에도 — python 은
  `services/python/tests/test_foo.py`, node 는 vitest 관례대로). 고칠 계획이 없어도 넣는다 —
  검증 단계가 소스 변경을 확인하려고 그 테스트를 고치는 순간 죽는다. 설계가 가장 자주 빠뜨리는 자리다.
- 파일명이 구현 시점에 정해지는 것(마이그레이션 revision 등)은 설계에서 이름을 **직접 정해**
  완전한 경로로 적는다. 자리표시자는 목록이 아니다.
- 목록이 길어지는 게 부담이면 설계 범위가 넓은 것이다. 목록을 줄이지 말고 범위를 줄여라.
- **여기 넣는 기존 파일은 전부 Read 로 열어봐야 한다.** 셸이 이 세션의 도구 호출 기록에서
  확인하고, 안 읽은 파일이 하나라도 있으면 판단 검증을 띄우지 않고 죽인다. 열어보지 않은
  파일을 고치겠다는 설계는 그 자체가 누락이다. Grep 으로 스친 것은 읽은 것이 아니다.

## TEST_FILES 블록 (형식 엄수 — 셸이 파싱한다)

`ALLOWED_FILES` 중 **테스트 파일만** 다시 적는다. 같은 형식, 같은 규칙이다.

TEST_FILES:
- test/foo.test.ts

셸은 이 블록으로 "누가 어느 파일을 고쳐도 되는가"를 가른다 — 구현 단계는 여기 있는 파일을
바꾸면 죽고, 검증 단계는 여기 **없는** 파일을 바꾸면 죽는다. 그래서:
- 검증이 고쳐야 할 기존 테스트(낡은 테스트)와 새로 만들 테스트를 전부 넣는다.
- 소스 파일을 여기 넣지 않는다 — 검증이 소스를 땜질할 수 있게 되고, 그건 이 블록이 막으려는 것이다.
- 블록은 반드시 있어야 한다. 테스트 파일이 없는 설계라면 헤더만 쓰고 빈 줄로 닫는다.
- 여기 있는 파일은 `ALLOWED_FILES` 에도 있어야 한다. 아니면 설계 직후 죽는다.
- **검증 단계는 구현 전에 돈다.** 이 블록이 비어 있지 않으면 셸이 테스트 작성 뒤 구현 전 코드에서
  검증 명령이 **실패하는지**(red) 확인하고, 통과하면 죽인다. 동작을 바꾸지 않는 변경(리팩터·문서·설정)은
  red 가 날 수 없으니 블록을 비워라 — 그때는 기존 테스트가 통과하는지만 본다.

## 게이트에 걸리는 것 — 설계에 넣지 말고 STATUS: BLOCKED 로 올려라
- 의존성 추가/제거 (`services/node/package.json`·`services/python/pyproject.toml` 등 — 사람 승인 사항)
- 테스트 러너·린터·타입 검사 설정 변경 (`tsconfig.json`·`.eslintrc.cjs`·`tests/conftest.py` 포함)
- 셸이 보호하는 파일(`PROTECTED_FILES`)을 바꿔야만 되는 설계

## 금지
- 코드를 쓰지 않는다. 시그니처와 스펙까지만.
- 설계에 필요한 정보가 없으면 추측하지 말고 `STATUS: BLOCKED`.
- **핸드오프·계획 문서를 수정하지 않는다.** 이 단계의 산출물은 `$WORK/DESIGN.md` 하나다.
