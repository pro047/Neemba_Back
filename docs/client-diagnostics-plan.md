# 앱 진단 기록 서버 수집 계획 (client-diagnostics)

작성 2026-11-18. 이 문서가 정본이다. 서버(neemba) 범위만 구현한다 — 앱(mvp 리포)은 mvp 세션이 이 문서의 계약을 보고 따로 구현한다.

## 왜

- 2026-11-15 예배: 서버는 02:09 에 청취자 소켓 1006 끊김을 기록했고 그 뒤 번역 529건이 폐기됐다
  (`app.ws_blips` lost_count, 실측). 원인 경로 후보가 셋인데 서버 기록만으로는 가를 수 없다 —
  ① 앱이 죽은 소켓을 모름(앱 발신 ping 없음) ② 241초 재시도 예산 소진 후 미재시작 ③ 백그라운드/화면 잠금.
- 앱에는 이걸 가를 진단 기록(`diagnostics.log`)이 있지만 기기 안에만 있고, 받으려면 기기를 직접 만져야 한다.
- 컨테이너 로그는 배포 때 지워진다(2026-08-17 실측 — 8/16 예배분 유실). 그래서 **DB 테이블**에 쌓는다.

## 사용자 확정 결정

1. 실시간 조회 불필요 — 예배 후에 본다.
2. **즉시 전송이 아니라 저장 후 일괄 전송(store-and-forward).** 끊긴 순간의 기록은 그 순간 보낼 수 없으므로,
   기기 파일에 쌓아 두었다가 아래 시점에 미전송분을 올린다:
   ① `/ws` 재연결 성공 직후 ② 앱 실행 시 ③ 세션 시작 성공 시
   (③은 mvp 세션 지적으로 추가 — 예산 소진 후 재시작은 재연결이 아니라 첫 연결이라 ①이 불리지 않는다, mvp `ws_client.dart:221-224`)
3. 저장소는 DB 테이블(스키마 `app`, 마이그레이션 추가). 컨테이너 로그 아님.
4. 서버 구현은 이 파이프라인, 앱 구현은 mvp 세션. **계약(아래)은 설계 게이트에서 사람이 승인한 뒤 고정한다.**

## 앱 쪽 현실 (mvp 세션 보고, 2026-11-18 — 계약이 이걸 전제로 해야 한다)

- 기록 한 줄 형식: `<UTC ISO8601> <event> k=v k=v ...` — JSON 아님. 값은 공백 1칸으로 접히고 200자(`frames` 1200자)에서
  잘려 `…` 가 붙는다. null=`<null>`, 빈 값=`<empty>`. 따옴표·이스케이프 없음 → 값에 공백·`=` 가 있으면 필드 경계 복원 불가.
- 시각: UTC, `Z` 접미, 소수부 3자리 또는 6자리 가변(예 `2026-11-18T10:18:15.988504Z`, `2026-11-15T02:09:00.123Z`).
  벽시계라 역행 가능 → 정렬 키로 쓰면 안 된다.
- 기록 고유 번호·기기 식별자 없음(현재). 앱이 새로 만든다: 설치 ID(최초 실행 UUID) + 단조 증가 seq.
- 기기 보관 상한: 파일 256KB × 2개(회전). 오프라인으로 그 이상 쌓이면 앞부분은 업로드 전에 사라진다(설계상 상한) →
  서버에서는 seq 빈 구간으로 드러나야 한다.
- 인증 수단 없음: 앱 REST 요청 헤더는 Content-Type 뿐(Authorization 0건).
- 마스킹: 세션 id 는 앞 8자리만 남긴다(`maskId`). 단 연결 실패 예외 메시지에 sessionId 가 든 전체 URL 이 남을 수 있다(미확인) →
  **앱이 업로드 전에 URL 마스킹을 적용하는 것을 계약 조건으로 둔다.**

## 계약에 담을 것 (설계가 구체값을 정하고 사람이 승인)

- 엔드포인트 경로와 어느 서비스가 받는가. 참고: nginx 에서 `/api/` 는 node 로, `/api/monitor/` 는 python(+Basic Auth)으로 간다
  (`infra/nginx/nginx.conf:53`, `:110`). 마이그레이션·DB 쓰기는 python 쪽이다. 앱은 Basic Auth 를 못 넘기므로 `/api/monitor/` 아래는 불가.
- 요청 본문: `install_id`, 앱 버전(있으면), 기록 배열 `[{seq, line}]`. **서버는 줄 원문(line)을 통째로 저장**하고
  ts·event 만 파싱해 별도 컬럼에 둔다(파싱 실패해도 원문은 저장). 필드(k=v) 구조 파싱은 하지 않는다.
- 멱등: `(install_id, seq)` 유일. 같은 쌍이 다시 와도 1행.
- 크기 상한: 기기 최대 보관량(약 512KB)을 기준으로 정한다. 초과는 413. 줄 1개 길이 상한도 둔다.
- 응답 코드 의미 — 앱이 재전송 여부를 이걸로 판단한다:
  성공(중복 포함) / 재전송하면 안 되는 거부(형식 오류·413) / 재전송해도 되는 실패(5xx·타임아웃).
  앱이 "어디까지 올렸나"를 갱신할 수 있도록 성공 응답에 서버가 받아들인 seq 범위(또는 최대 seq)를 돌려준다.
- 무인증 엔드포인트다 — 크기·형식 검증으로 막는다. 레이트 제한이 필요하면 설계가 근거와 함께 제안한다.
- 계약 문서는 `docs/client-diagnostics-contract.md` 로 따로 쓴다 — mvp 세션이 이 파일만 보고 구현할 수 있어야 한다.

## 완료 조건 (M1, 사용자 승인)

1. 같은 기록(같은 install_id·seq)을 두 번 보내도 DB 에 1행만 남는다 — 자동 테스트
2. 크기 상한을 넘는 요청은 413 — 자동 테스트
3. 마이그레이션 upgrade·downgrade 통과
4. 기존 테스트 전체 통과(python pytest, node test, tsc)
5. 계약 문서 `docs/client-diagnostics-contract.md` 사람 승인(설계 게이트)

## 하지 않는 것

- 앱(mvp 리포) 코드 — mvp 세션 몫
- 모니터 UI 화면 — 조회는 다음 마일스톤(M3: `ws_blips` 끊김 1건 기준 ±5분 앱 기록을 보는 SQL)
- 실시간 조회·알림
- 기록 필드(k=v) 구조 파싱
