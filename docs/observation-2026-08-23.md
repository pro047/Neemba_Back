## 2. 수집 경로 정정 — 번역문은 DB 에 있다

핸드오프와 `watch-service` 스킬 런북 양쪽의 서술이 틀렸다.

| 문서가 말한 것 | 실제 (실측) |
|---|---|
| "번역문은 DB 에 없다. public 스키마는 `alembic_version` 뿐" | `public` 만 본 것. 데이터는 **`app` 스키마**에 있다 — `app.sessions`(45행) · `app.translations`(4,512행) · `app.ws_blips`(18행) |
| "원문은 node `published :` 로그에 있다 → 배포 전 파일로 내려받을 것" | `app.translations` 에 `source_text`(한국어) + `translated_text`(영문)가 **쌍으로** 저장. `pg-retention` 로그 기준 **보존 30일**(`window=30d, interval=24h`) |

**왜 중요한가.** `published :` 로그는 interim 델타 조각이라 `나뮤`+`다` 로 쪼개진 것을
사람이 이어붙여야 한다. DB 는 **문장 단위 확정 쌍**이라 `transcriptNormalization` 표의
1차 소스로 훨씬 낫고, 로그 롤오버(`max-size 10m`)·배포 삭제 위험도 없다.

**로그가 무용하지는 않다** — interim 단계에만 나타나고 final 에서 교정되는 오인식은
DB 에 안 남는다. 두 소스를 병행하되 1차는 DB.

오늘 회수분: `~/neemba-logs/source-2026-08-23-final.txt` (4,260줄).

**메커니즘 확정 (2026-08-23 코드 확인)** — 오디오 재전송 가설은 **기각**한다.
node 는 오디오를 재전송하지 않는다. 실제 경로는 이렇다:

1. STT 정체 후 Google 이 이전 구간을 다시 실어 보낸다
2. node `InterimChunkOrchestrator` 는 **직전 final 을 처리하며 이미 리셋된 상태**다 —
   `this.prevText = ""; this.text = "";` (`usecases/InterimChunkOrchestratotr.ts:77-78`)
3. 다시 온 텍스트로 델타를 계산하는데 `computeDelta` 가
   `if (!prevText) return currText;` (`:103`) 로 **전체를 델타로 반환**한다
4. 그대로 새 `sequence` 를 달아 publish (`:160`)
5. **중복 제거 세 층이 전부 통과한다** — 전부 sequence 기반이기 때문:
   - JetStream `Nats-Msg-Id = ${sessionId}:${sequence}` (`js_pub.ts:101`)
   - node 재시도 버퍼의 워터마크 (`retryingPublisher.ts:11` 주석)
   - python `_is_duplicate`: `req.sequence <= last` (`src/consumer/consumer.py:209`)

   재송출분은 sequence 가 **더 크므로**(2207 → 2262) 셋 다 정상 통과한다.

**근본 원인**: 파이프라인 전체에 **내용 기반 중복 제거가 한 층도 없다.** sequence 는
항상 증가하므로 같은 문장이 다시 흘러도 막을 방법이 없다.

**로그 교차 검증 (실측)**: 회수한 `published` 로그에서 `축복인지` 가 2회 나온다 —

### 6-1. ~~`transcriptNormalization` 을 어디에 붙일 것인가~~ — **질문이 틀렸다 (2026-08-23 정정)**

**초안 서술 (틀렸다)**: "`InterimChunkOrchestratotr.ts:94` 의 `normalize()` 훅에 붙이면
델타 계산 전이라 조각 단위로 적용된다 → 문장 단위인 python `kss_separator.py:281-290`
이 유력하다."

**두 군데가 틀렸다.**

**① `transcriptNormalization` 은 우리 코드 층이 아니다.** Google STT v2
`RecognitionConfig` 의 필드다 — 핸드오프 §7(2026-08-17 실스트림 프로브 실측)이 이미
확정했다. Google 이 **전사문에 적용한 뒤** 우리 델타 계산이 돌므로 경계 문제가 원천
없고, 채택은 `googleSttV2.ts` 의 request config 에 **필드 1개 추가**다.
→ **"어디에 붙일 것인가" 라는 결정 자체가 존재하지 않는다.** 초안이 node 의
`normalize()` 훅을 보고 "우리 코드에 치환표를 넣는 작업" 으로 오해해 없는 갈림길을
만들어냈다.

**② 설령 우리 코드에 넣는다 해도 `normalize()` 는 "조각 단위" 가 아니다.**
`InterimChunkOrchestratotr.ts:44` 가 `normalize(result.transcript)` 를 부르고, 그
`transcript` 는 `googleSttV2.ts:67` 의 `alternative.transcript` — Google interim 의
**누적 가설 전문**이다. 델타는 그 **뒤**에 `computeDelta` 가 직접 계산한다. 즉
`normalize()` 는 `고구마율` 을 온전히 본다.

**그래도 그 자리는 부적합한데, 이유가 다르다.** 델타 스트림은 append-only 라 **이미
내보낸 접두사를 회수할 수 없다**:

```
interim N   : "일본 땅에서 고구마"          → 규칙 미매칭 → 이미 publish 됨
interim N+1 : "일본 땅에서 고구마율이 낮은" → "일본 땅에서 복음화율이 낮은"
computeDelta(prev="…고구마", curr="…복음화율이 낮은") → "복음화율이 낮은"
시청자 화면: "일본 땅에서 고구마" + "복음화율이 낮은"
```

교정이 아니라 **중복**이 된다. 규칙이 언제 매칭되느냐가 타이밍에 달려 있어 재현도
불규칙하다. 같은 이유로 **우리 코드의 사후 치환은 STT 레벨 정규화보다 항상 불리하다** —
§7 이 "조각화가 오히려 STT 레벨 정규화를 지지하는 근거" 라고 쓴 것이 이 이야기다.

**그래서 큐 1 에 실제로 남은 일**은 적용 지점 판단이 아니라 세 가지다:

1. §3-2 표를 `transcriptNormalization` entry 목록(`search`/`replace`)으로 옮긴다
2. `에서`(Esau) 처럼 조사와 동형인 것은 **넣지 않는다** — §3-1 참조. 결정론적 치환이라
   `이들은에서` 를 고치려다 `…에서` 조사를 전부 망친다
3. **과보정 A/B 검증** — §7 말미의 절차(타깃 재현율뿐 아니라 오삽입 수·목록 밖 WER·
   final latency 를 함께 본다). 한국어에서 `아멘↔아무`·`다윗↔다음`·`이삭↔이사` 가 위험

**따라서 큐 1 과 큐 2 는 같은 결정이 아니다.** 큐 2 만 설계 판단이 남아 있다.
