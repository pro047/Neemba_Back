| 항목 | 결과 |
|------|------|
| 번역 총량 | 약 550건 (10:51~11:27 KST, 37분) |

### 4-1. 순단 3회 — handover §4-7 가설 ① 쪽 근거가 쌓였다

```
02:02:17 → 02:02:18 UTC   1초,  flushed 4,  유실 0   (정상 복구)
02:13:20 → (재연결 없이 02:13:27 세션 종료)          → 세션 5회 교체로 이어짐
02:27:36 → (재연결 없음, keepalive 300s 타임아웃)     → 예배 종료
```

**7/26 예배 순단 3회도 전부 1006 이었다.** 두 예배 연속으로 1001(기기 정상 종료)이
한 건도 없다는 것은 절전·백그라운드 전환(가설 ②)보다 **네트워크 불안정(가설 ①)**
쪽을 가리킨다. 다만 §4-7 이 제안한 현장 조치(Wi-Fi↔LTE 전환 비교)는 아직 미수행이라
확정은 못 한다.

### 4-2. 세션 5회 교체 — **원인 미확인**

```
02:13:27  세션 2d3aa2ab 종료 (끊긴 지 7초 만에 = 명시적 stop 호출)
02:13:27  → ca1e261b  (21초 후 종료)
02:13:48  → d4039f1b  (48초 후 종료)
02:14:37  → fd6ae34b  (96초 후 종료)
02:16:13  → e01b46f0  ( 8초 후 종료)
02:16:21  → 0d79c3ef  ← 안정화
```

각 종료마다 `publish buffer: span dropped after stop` 이 찍혀 **총 5개 span 이
유실**됐다. keepalive 는 300초까지 기다리게 돼 있는데 7초 만에 `stopped` 가 찍혔으니
서버가 죽인 것이 아니라 **명시적 stop 호출**이다.

**사용자 확인 결과: 본인이 한 것이 아니다.** 현장 다른 조작인지 자막 앱의 재기동
루프인지 미확정. 다음 예배에서 같은 패턴이 재발하는지 관찰할 것.

### 구현한 것

  **렌더 경로의 `$()` 는 의도적으로 남겼다** — 조용한 no-op 은 진단을 막는다.
  다음 사람이 "일관성" 명목으로 60여 곳을 `$opt` 로 바꾸지 않도록 주의.

- **③ 칩 보존** — 실패 시 기존 칩을 두고 "조회 실패" 만 덧붙인다. `statusStale` 로

### 코드리뷰가 잡은 3건 (전부 반영)

1. **`sessionsState.loading` 고착 — 내가 만든 회귀.** ①의 `try/catch` 가 예외를
   삼키는데, `loadSessions` 는 플래그를 세운 **뒤에** `clear($("session-list"))` 를
   부른다. 여기서 던지면 `.finally` 에 영영 못 닿아 플래그가 true 로 굳고,
   refreshSessions·새로고침·WS 복구가 전부 no-op 이 된다. 예전엔 페이지가 눈에 띄게
   죽었는데 **조용히 죽는 쪽으로 바뀐 것이라 더 나빴다.** 플래그 세팅을 동기 DOM
   작업 뒤로 옮겨 해소(그 구간은 콜백이 못 끼어들어 재진입 위험 없음).
2. **WS 재연결 영구 중단 (기존 결함).** `scheduleRetry` 가 `setTimeout` **앞에서**
   `opts.onDown()` 을 부르는데, 그 콜백들이 `$("detail-status")`·`$("sessions-status")`
   를 쓴다. 스큐로 그게 없으면 재연결이 영영 예약되지 않는다. 두 줄 순서를 바꿔 해소.
3. **상태 폴링 에러 삼킴.** `.catch(markStatusStale)` 이 `err` 를 버려서, `renderStatus`
   가 던진 경우도 "조회 실패" 칩으로 보인다 — 백엔드가 멀쩡한데 백엔드를 뒤지게 된다.
   `console.error` 를 먼저 찍게 수정.

### 이 세션에서 테스트가 두 번 틀렸다 — 둘 다 계측 대상을 잘못 골랐다

1. **"서버가 받은 요청 수" 로는 in-flight 가드를 측정할 수 없다.** 첫 라운드에서 ②
   두 건이 수정본·되돌린 빌드 **양쪽 다 통과**했다. 계측해 보니 페이지가 6번 `fetch`
   했는데 서버는 0건을 받았다 — **Chrome 이 같은 URL 의 미완료 GET 뒤로 중복 요청을
   캐시 엔트리 락에 세운다.** CDP `Page.addScriptToEvaluateOnNewDocument` 로 app.js
   보다 먼저 `window.fetch` 를 감싸 **페이지가 시도한 횟수**를 세도록 바꾸니 1 vs 3 /
   2 vs 3 으로 갈렸다. 가드가 바꾸는 것은 시도 횟수이지 서버 수신 수가 아니다.
2. **하니스가 WS 업그레이드를 거절해 재연결 배너가 `#sessions-status` 를 덮고 있었다.**
   무관한 단정이 깨졌다. 최소 RFC6455 핸드셰이크만 응답하게 해 오염을 제거했다
   (`sha1(key + 258EAFA5-E914-47DA-95CA-C5AB0DC85B11)` → base64, 프레임은 안 보냄).

**통과하는 테스트는 그 자체로 아무것도 증명하지 않는다** — 8/5 에 배운 것과 같은
교훈인데, 이번엔 대조군이 "테스트가 무의미함" 을 알려준 쪽이었다. 대조군이 없었다면
②는 통과 표시를 달고 아무것도 안 지킨 채 배포됐다.

### 남긴 것 (§2 큐 4번)

- **`loadHistory`·`runSearch`·`loadBlips` 도 `loadSessions` 와 같은 모양이다** —
  플래그를 세운 뒤 `clear($(...))` 를 부른다. 던지면 해당 패널이 영구히 잠긴다.
  고치지 않은 이유: 이 셋은 클릭·탭 진입으로만 호출돼 **`try/catch` 가 덮지 않아**
  예외가 콘솔에 그대로 뜬다. 즉 이번 변경으로 나빠진 게 없다. 각각 한 줄 이동.
- **`fetchJson` 에 타임아웃(`AbortController`)이 없다.** 끝나지 않는 요청 하나가 해당
  폴러를 nginx `proxy_read_timeout`(기본 60s)까지 멈춘다. 코드리뷰는 이걸 ②의 회귀로
  불렀지만 **그 판정은 틀렸다** — 위 1번에서 밝혀진 캐시 락 때문에 수정 전에도 실패
  칩은 안 떴다. 회귀가 아니라 기존 사각지대이고, 504 후 자동 회복된다.
