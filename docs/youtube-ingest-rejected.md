# 유튜브 링크 수집 — 조사 기록 (기각)

**결론: 기각.** prod 의 데이터센터 IP 가 유튜브 봇 차단에 걸려 수집이 불가능하다.
2026-08-09 에 실측으로 판정했다. **이 문서는 구현 지시서가 아니라 "왜 접었나"의
근거 기록이다** — 다시 꺼내기 전에 §2 의 실측 표부터 읽어라.

사용자 요구는 *"rtmp 가 아니라 유튜브 링크 입력했을 때 현재 rtmp 와 동일하게
기능이 되어야 해"* 였고, 대상은 **타 교회 방송**이었다.

## 1. 배경 — 이건 신규가 아니라 재도전이었다

프로젝트 최초 형태(`e7344f3` init project)가 정확히 유튜브 수집이었다:
`YtDlpProcess`(yt-dlp 로 재생 URL 해석, 쿠키 + 클라이언트 6종 폴백) →
`StreamlinkProcess`(HLS 읽기) → ffmpeg → STT. **유튜브에 막혀서 RTMP 로 갈아탔고**
(`0cfd408` fixed rtmp), 어댑터 2개가 삭제됐다(`43b7e6c`).

옛 구현: `git show e7344f3:services/node/src/adapters/YtDlpProcess.ts`

즉 **한 번 실패한 길을 다시 판정한 것**이고, 결과는 같았다. 다만 이번엔
**실패 지점을 정확히 특정했다** — 그게 이 문서의 값이다.

## 2. 실측 (2026-08-09) — 판정의 근거

대상은 실제 라이브(`말씀을 노래하다`, `9RNJZGMVSQ4`, `is_live` 확인).
쿠키는 브라우저 전체 내보내기에서 `.youtube.com` 43줄만 걸러낸 것(인증 쿠키 8종
각 1개, 만료 2027-09). **같은 URL·같은 쿠키·같은 yt-dlp(2026.07.04)** 로 IP 만 바꿨다.

| 조건 | 로컬 (가정용 IP) | prod (데이터센터 IP) |
|---|---|---|
| 쿠키 없음 | — | ❌ `Sign in to confirm you're not a bot` |
| 쿠키 O | ✅ **PCM 320,000 bytes / 10초 (100%)** | ❌ 동일 차단 |
| 쿠키 O + deno(JS 런타임) | — | ❌ 동일 차단 |
| 쿠키 O + deno + **PO 토큰 사이드카** | — | ❌ 동일 차단 |

- 로컬은 `-f 91`(256x144 HLS) → `ffmpeg -vn -ac 1 -ar 16000` 으로 **10초치 PCM 이
  정확히 320,000 bytes** 나왔다. 방법도 쿠키도 멀쩡하다는 뜻이다.
- **차단 축은 순수하게 IP.** 다른 변수는 전부 통제됐다.
- 마지막 수단이던 `bgutil-ytdlp-pot-provider`(v1.3.1, `/ping` 정상 응답,
  `neemba_appnet` 에 붙여 컨테이너에서 도달 확인)도 **뚫지 못했다.**
  이게 "이번 재도전의 유일한 새 변수"였고 소진됐다.

### 2-1. 함정 — yt-dlp 버전이 증상을 위장한다

로컬에서 **낡은 yt-dlp(2025.08.11)** 는 전혀 다른 에러를 냈다:

```
2025.08.11 →  ERROR: The following content is not available on this app.
2026.07.04 →  정상 해석
```

앞 문구는 **옛 코드 `YtDlpProcess.isPolicyBlock` 이 잡던 바로 그 문자열**이다.
즉 초기에 클라이언트 6종을 돌려막던 것은 이 증상 우회 시도였고, **버전 노후와
IP 차단이 같은 문구로 보이지 않는다는 걸 모른 채 헤맸을 가능성이 크다.**
다시 조사할 일이 생기면 **yt-dlp 를 먼저 최신으로 맞추고** 판정할 것.

## 3. 뚫으려면 남는 수단 — 전부 별개 인프라

- **레지던셜 프록시** — 주거용 IP 를 빌린다. 비용·신뢰성·약관 문제가 새로 생긴다.
- **교회 네트워크에 상시 머신** — 거기서 오디오만 서버로 릴레이. 그런데 **교회에
  기계를 둘 수 있으면 그 기계가 그냥 RTMP 를 쏘면 된다**(지금 구조 그대로).
  유튜브를 경유할 이유가 사라진다.

**둘 다 "유튜브 링크만 넣으면 된다"는 원래 요구를 만족시키지 못한다.**

## 4. 부수 발견 — 지금 이미지의 죽은 도구 2건

프로브 중 **현재 배포본의 도구가 죽어 있는 것**을 확인했다.

- **`yt-dlp` 는 실행 자체가 안 된다.**
  `ImportError: Only Python versions 3.10 and above are supported by yt-dlp`.
  베이스 이미지 `node:22-bullseye`(Debian 11)의 시스템 파이썬이 **3.9** 다.
  **오늘(2026-08-09 15:30) 빌드된 최신 이미지에서도 동일** — 다시 빌드해도 깨진다.
- **`streamlink` 2.0.0** (현재 7.x). Debian 11 저장소 화석.

지금은 아무도 안 쓰는 경로라 무해하지만, 매 빌드마다 깨진 것을 설치하느라 시간과
용량을 쓴다. **남겨두면 다음 사람이 "설치돼 있으니 되겠지"로 오판한다** →
`Dockerfile` 에서 제거했다(이 문서와 같은 브랜치).

되살릴 일이 생기면 **시스템 파이썬에 의존하지 말고 `yt-dlp_linux` 독립 실행
바이너리**를 쓸 것(파이썬 내장). 프로브에서 그 방식으로는 정상 기동했다.
JS 런타임(deno)도 별도 의존성으로 필요하다 — 없으면 일부 포맷이 누락된다(EJS).

## 5. 약관·저작권 (판정과 무관하게 남기는 기록)

- yt-dlp 풀 자체가 유튜브 약관의 **자동화 접근 금지** 위반이다. 제재는 현실적으로
  계정 단위. 그래서 프로브에도 본계정이 아니라 **필터링한 쿠키**만 썼고, 실제
  운영에 갔다면 **버너 계정 전용**이 불변식이었다.
- 대상이 **타 교회 방송**이면 번역·전송은 방송 주체 허락이 있어야 깨끗하다.
  시스템은 링크 주인을 구분할 수 없으므로 **허락 여부는 입력자 책임**이다.
  코드가 대신 판단할 수 없는 영역이다.

## 6. 대안 — 마이크 모드로 간다 (사용자 결정)

풀이 막히면 마이크로 간다는 것이 착수 시점의 결정이었다(Y4). **서버 경로는 이미
있다** — 오디오 입구만 다르고 STT→NATS→번역→청취자 팬아웃은 RTMP·mic 가 공유한다
(`runMicPipeline.ts` 와 `runPipelines.ts` 가 같은 `createStreamOrchestrator` 를 쓴다).

**다만 prod 에서 지금 그대로는 동작하지 않는다. §7 참조.**

## 7. 마이크 모드 현황 (2026-08-09 코드 직독) — **prod 차단 요인 1건**

### 있는 것

| 계층 | 상태 |
|---|---|
| node REST | `POST /api/mic/start` · `/mic/stop` · `/mic/tts` (`router/mic.ts:412-414`) |
| node WS | `/api/mic` (`micWebSocket.ts:154` 기본 path), `app.ts:69` 에서 서버에 부착 |
| node 파이프라인 | `runMicPipeline.ts` — RTMP 와 **같은** `createStreamOrchestrator` |
| 유령 세션 방어 | 소켓이 stop 없이 닫히면 유예 후 teardown, 재접속 시 취소 (`micWebSocket.ts:73·107`) |
| 앱 | `MIC` 탭이 **이미 있다** (`mode_select_screen.dart`, 2탭 중 하나). `mic_translation_tab.dart` 450줄, 오디오 캡처·서버 TTS 포함 |

### 막는 것 — **prod nginx 에 `/api/mic` 웹소켓 블록이 없다**

```
dev  infra/nginx/dev/nginx.conf:31   location /api/mic { ... Upgrade ... }   ✅ 있음
prod infra/nginx/nginx.conf          없음 → location /api/ 로 떨어진다      ❌
```

`location /api/`(`nginx.conf:107`)에는 **`Upgrade`/`Connection` 헤더가 없고**
`proxy_read_timeout` 이 **30초**다. 따라서 prod 에서 `/api/mic` 웹소켓은

1. 업그레이드 헤더가 안 실려 **핸드셰이크가 성사되지 않고**,
2. 설령 붙어도 30초에 끊긴다.

**즉 마이크 모드는 dev 에서만 동작하고 prod 에서는 깨져 있다.** 앱에 탭이 보이므로
"되는 줄 알고" 쓰면 원인 모를 실패를 겪는다.

**수정**: dev 블록(`dev/nginx.conf:31-46`)을 prod 로 옮긴다. `/api/` 보다 구체적인
prefix 라 nginx 가 먼저 매치한다 — `/api/monitor/` 가 이미 같은 방식으로 앞선다.
`proxy_read_timeout 3600s` + `proxy_buffering off` 도 함께 가져와야 한다.

### 그다음 확인할 것 (코드로는 판정 불가)

- 실기기에서 마이크 권한·오디오 포맷(샘플레이트·인코딩)이 STT 가 기대하는 것과 맞는지
- 예배 환경에서 **현장 마이크 오디오 품질**이 STT 에 쓸 만한지 — RTMP 는 믹서 출력이라
  깨끗했지만 기기 마이크는 잔향·군중 소음이 섞인다. **이게 마이크 모드의 진짜 리스크다**
- `POST /api/mic/tts` 가 있는 것으로 보아 서버 TTS 경로가 별도로 있다 — 청취자
  팬아웃(`/ws`)과 어떻게 갈리는지 확인 필요
