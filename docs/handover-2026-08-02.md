**게이지 라벨화 검증 상태 (2026-08-17 prod 실측)**

모니터 **화면**으로는 신·구를 구분할 수 없다(세션 0개면 양쪽 다 0으로 보인다).
**하지만 원시 `/metrics` 는 구분된다** — 이 방법으로 배포를 확인했다:

```
docker exec node curl -fsS localhost:3000/metrics | grep -E '^neemba_(stt_paused|publish_buffer_size)'
# → 0줄  (신코드: 세션 0개면 샘플 라인이 없다. 구코드는 `neemba_stt_paused 0` 을 항상 냈다)
docker exec node curl -fsS localhost:3000/metrics | grep '^neemba_rtmp_auth_enabled'
# → neemba_rtmp_auth_enabled 1   (대조군: 무라벨 게이지는 샘플이 있다 = 스크레이프 실패가 아님)
```

**대조군을 반드시 함께 볼 것.** "0줄" 만 보면 스크레이프 실패와 구분되지 않는다.

확인된 것: ① 라벨드 게이지 형태로 배포됨 ② `# TYPE` 시딩 경로가 살아 있음 —
상태 API 가 `sttPaused:false`·`publishBufferSize:0` 을 반환(시딩이 없으면 `null`)
③ `rtmp_auth_enabled` 가 **시딩되지 않고 실제 값 1** 을 반환(리뷰 수정 #4 가 의도대로 동작).

**남은 미검증분**: 세션별 시리즈 독립성(은폐 시나리오)과 종료 시 시리즈 제거.
둘 다 **세션이 실제로 떠야만** 확인된다 (§2 큐 1번).

**검증 방식은 항목의 성격이 정한다.** 모니터 안정성 3건은 예배 없이 헤드리스
Chrome 으로 재현·해소를 둘 다 봤다(9/9 + 음성 대조군 6건). 반면 WU-F·V3-A·게이지
라벨화는 **실제 세션이 떠야만** 판정된다 — 이 구분을 지키지 않으면 "테스트 통과" 를
"검증 완료" 로 착각하게 된다.

**"prod 에서 안 된다" 를 버그로 판정하기 전에**, 이제는 미배포가 아니라
**브라우저 캐시**를 먼저 의심할 것 (§5 참조).

### 8/19 검증 항목

1. **live 세션이 2개 동시에 뜨는가** — RTMP + 마이크. 이게 안 되면 이하 무의미

3. **종료 시 시리즈가 사라지는가** — 세션을 끝낸 뒤 그 `sessionId` 라벨이 `/metrics`

**4번이 "상태 미확인" 인 이유.** 8/9 주일예배는 실제로 있었고 그날 커밋도 여럿

## 2-1. WS 재연결 계약 (2026-08-17 신설 — 클라이언트가 참조하는 값)

Flutter 재연결 예산의 근거다. **"서버가 끊김 후 300초 동안 pending 큐를 유지한다"
는 전제는 지금 코드에 없다** — 멀티 청취자 P1(#81)이 백로그(`_pending`)를 통째로
들어냈다(`websocket.py:17-20` 근거, `:616` 이 "300초 대기는 사라졌다"를 명시).
순단 구간 자막은 유실이고 유실량만 `ws_blips.lost_count` 로 남는다.

> **줄번호는 이 문서를 쓴 시점(2026-08-17) 기준이다.** 상수 이름으로 grep 하는
> 편이 안전하다 — 실제로 이 절의 초안이 자기 diff 때문에 어긋난 번호를 실었다.

### 세션 수명

| 항목 | 값 | 근거 (상수명) |
|---|---|---|
| 다운링크 끊김 후 유지 | **없음(무기한)** — 세션은 안 죽는다 | `websocket.py:364` `handle_client_disconnect` docstring |
| 업링크 끊김 후 유예 | **10초** → 세션 종료 | `DEFAULT_TEARDOWN_GRACE_MS` (`micWebSocket.ts:17`) |
| 업링크 반열림 탐지 | 15초 주기(최대 ~40초까지) | `DEFAULT_HEARTBEAT_INTERVAL_MS` (`micWebSocket.ts:21`) |
| start 후 첫 소켓 대기 | 15초 | `MIC_CONNECT_GRACE_MS` (`router/mic.ts:221`) |
| RTMP publisher_done 유예 | 120초 (env 조정) | `DEFAULT_PUBLISH_DONE_GRACE_SEC` (`router/rtmp.ts:14`) |
| 다운링크 keepalive | ping 30초 / pong 타임아웃 60초 (**소켓만** 버림) | `_PING_INTERVAL_SECONDS`·`_PONG_TIMEOUT_SECONDS` (`websocket.py:57-58`) |

**세션의 생사는 시간이 아니라 `_sessions` 등재 여부**이고, 빠지는 경로는 `detach`
하나뿐이다(`websocket.py:291`). 시간 기반 만료는 없다 — `close_stale_sessions` 는
startup 1회 도는 **DB 전용** 정리라 허브를 안 건드린다.

**따라서 마이크는 업링크가 세션 수명을 지배한다.** 업링크 백오프 상한이 10초를
넘으면 그 시점에 세션은 이미 죽어 있다.

### close code (2026-08-17 A그룹으로 정비)

| code | 의미 | 클라이언트 동작 | 근거 |
|---|---|---|---|
| `1008` | sessionId 쿼리 누락 | 중단 (버그) | `main.py:629` (다운링크) · `micWebSocket.ts` 접속 가드 |
| `4404` | 그 세션이 없다 | **재시도 중단** | `CLOSE_SESSION_NOT_FOUND` (`websocket.py:48`) · `CLOSE_MIC_SESSION_NOT_FOUND` (`micWebSocket.ts:27`) |
| `4410` | 세션이 방금 끝났다 | **재시도 중단** | `CLOSE_SESSION_ENDED` (`websocket.py:55`) |
| `1000` | 소켓 하나만 떨어짐 (keepalive 등) | **재시도 계속** | `_drop_conn` 이 기본값 유지 |

**1000 과 4410 의 구분이 핵심이다.** 정비 전에는 세션 종료도 1000 이라 클라이언트가
한 번 붙어서 4404 를 받아야만 만료를 알 수 있었다. 이제 종료 프레임 자체가 4410 이다.

**`_drop_conn` 에는 만료 코드를 쓰면 안 된다** — 소켓 하나가 keepalive 로 떨어졌을
뿐 세션은 살아 있고 그 청취자는 재접속을 **해야 하는** 쪽이다. 대조군 테스트가
`tests/test_ws_close_codes.py` 에 있다.

업링크는 **접속 시점에** 검증한다(`micWebSocket.ts`) — 정비 전에는 첫 오디오
프레임이 와야 거절했다.

### `POST /api/mic/stop`

만료된 sessionId 로 불러도 **200** 이다(python stop 이 멱등). **200 을 "내가
끊었다" 로 읽지 말 것.** 대신 응답에 `ended` 가 실린다.

- `ended: true` — 이 호출이 세션을 끝냈다
- `ended: false` — **대개** 이미 끝나 있던 것이다 (오프라인 Stop 이 늦게 도달)

**`ended` 는 허브 상태가 아니라 DB 상태다** (`main.py:572-579` → `end_session`).
DB 풀이 없거나 `end_session` 이 예외를 내면 그 블록이 조용히 넘어가 `ended` 가
false 로 남는데, **그 뒤 `hub.detach` 는 정상 수행되어 세션은 실제로 끝난다.**
즉 RDS 페일오버·풀 소진 중에는 "내가 끊었는데 false" 가 나올 수 있고, **DB 없는
로컬 환경에서는 항상 false** 다.

→ 클라이언트는 `ended:false` 를 "이미 끝나 있었다" 로 **단정하지 말고** UI 를
어느 쪽으로도 무해하게(둘 다 '종료됨') 처리하는 편이 안전하다. 허브 기준의
정확한 답이 필요하면 `detach` 가 라이브였는지를 응답에 실어야 한다 — **후속
백로그**(`wasLive` 필드 추가, §6).

### 2026-08-17 추가

- **python 테스트는 반드시 `.venv/bin/python -m pytest`.** 시스템 python 으로 돌리면
  `prometheus_client`·`nats` 미설치로 **수집 단계에서 12건 에러**가 난다. 이걸 코드
  결함으로 오독하기 쉽다 — 임포트 에러가 뜨면 먼저 인터프리터를 의심할 것.

  한 명령으로 묶으면 거부된다.** 훅이 명령 시작 시점에 토큰을 보므로 **touch 를
  별도 명령으로 먼저** 실행해야 한다. 오래된 세션에서 커밋하려다 두 번 막혔다.

  결함으로 판정하지 말 것. 세션별 상세 노출은 후속 백로그.
- **배포 직후 "마지막 자막 전송 없음" 은 장애가 아니다.** 이 값은 python 프로세스
  메모리의 게이지라 컨테이너 재생성으로 0 이 된다. 오히려 **배포가 반영됐다는
  방증**으로 읽으면 된다.
- **게이지 시리즈는 teardown 이 커버하는 스코프 안에서만 시딩할 것.** 조립 시점
  (`createStreamOrchestrator`)에 시딩했더니, `start()` 가 끝내 호출되지 않는 실패
  경로에서 **지울 수단이 없는 시리즈**가 남았다 — 이 PR 이 막으려던 cardinality
  누수를 시딩이 되살린 꼴이었다. 시딩 1곳 · 제거 1곳 대칭을 깨지 말 것.

유력 후보(강함 → 약함):

1. **iOS: 버퍼마다 리샘플러 재생성** — 플러그인의 `ios/Classes/AudioCapture.swift:60`
   에서 `AVAudioConverter` 를 **탭 콜백 안에서** 만든다. 48k→16k 필터 상태가 약 100ms
   마다 리셋돼 프레임 경계마다 불연속이 생긴다. 앨리어싱은 아니지만 초당 10회 미세
   글리치다. **RTMP 는 ffmpeg 가 한 번에 리샘플하므로 이 문제가 없다 — "마이크만
   나쁘다" 는 관찰을 가장 잘 설명한다**
2. **iOS `.measurement` 모드로 AGC 전무**(`AudioCapture.swift:17`) + 앱에도 게인·정규화
   없음. 화자와 거리가 있으면 저레벨 신호가 그대로 나간다. 앱에 이미
   `lowLevelFrameCount` 계측이 있어(`audio_capture_service.dart:115`) **이 비율로 확정 가능**
3. **TTS 재생이 오디오 세션을 덮어쓴다** — `audioplayers` 기본 iOS category 가
   `.playback` 이라 캡처용 `.playAndRecord/.measurement` 를 덮는다. AEC 도 없어
   스피커 → 마이크 되돌이가 원 발화와 섞인다
4. Android 플러그인이 `read()` 반환값을 무시하고 항상 버퍼 전체를 전송 → 부분 읽기 시
   직전 잔여 오디오가 붙는다
5. 재접속 시 3초 초과분을 무음 대체 없이 버려(`node_ws_client.dart:181-187`) 시간축이 붕괴

**가장 먼저 계측할 값**: 플러그인이 내려주는 `actualSampleRate` 를 **앱이 한 번도 읽지
않는다**(`lib/` 참조 0건). 하드웨어가 16k 를 못 주고 폴백해도 앱은 모른 채 16k 가정으로
보낸다. 실 캡처 레이트 로깅이 1순위다.

**주의**: 후보 1·3·4 는 전부 **플러그인/서드파티 쪽 코드**다. 앱에서 고치려면 세션
설정을 앱이 직접 잡거나 플러그인을 교체·포크해야 한다 — 범위가 작지 않다.

### 조사 착수 ②: 성경 고유명사 STT adaptation (§2 큐 2번)

현재 speech adaptation 은 **어디에도 적용돼 있지 않다**(`services/node/src` 전체에
`adaptation`/`phraseSet`/`boost` 0건). 위 오역은 발화가 뭉개져서가 아니라 인식기가
그 단어를 후보로 갖고 있지 않아서 생긴다.

**확정된 것 (공식 문서 근거)**

- 필드는 `RecognitionConfig.adaptation` (`SpeechAdaptation`). **인라인 phrase set·
  리소스 참조 둘 다 가능**하고 node 클라이언트 타입에도 전부 존재한다
- **recognizer 를 건드릴 필요가 없다.** `StreamingRecognitionConfig.config` 는
  `configMask` 가 없으면 **비-기본값 필드가 recognizer 기본값을 덮어쓴다** — 현재
  코드는 mask 를 안 보내므로 `adaptation` 한 필드만 추가하면 된다. **배포 영향이
  node 코드 한 곳으로 국한되고 롤백은 상수 비우기**다 → 리소스 방식보다 인라인 권장
- boost 는 0 초과 20 이하, 구절 단위 override 가능. 쿼터는 요청당 5,000구절·
  10만자·구절당 100자. 다어절 구절은 **통째로만** boost 가 걸린다
- 추가 과금 없음(가격 페이지에 adaptation SKU 자체가 없음). **지연 영향은 미문서화**

**실측 결론 (2026-08-17, Locations API 직접 조회) — 현재 모델로는 불가**

`https://speech.googleapis.com/v2/projects/{proj}/locations?pageSize=100&filter=language = ko-KR`
를 이 프로젝트 자격증명으로 조회한 결과다. **`pageSize` 를 안 주면 5개만 오고
`nextPageToken` 이 붙는다 — us-central1 이 그 뒤 페이지에 있어서 처음엔 안 보였다.
페이지네이션을 반드시 처리할 것.**

us-central1 의 ko-KR 모델 5개와 adaptation(`speech_adaptation_boost`) 지원:

| 모델 | adaptation |
|---|---|
| `long` | **✗** |
| `chirp_2` | **✓** |
| `chirp` · `telephony` · `usm` | ✗ |

**`latest_long` 은 응답에 아예 없다** — `long` 의 레거시 별칭이고, 그 `long` 이
ko-KR 에서 adaptation 미지원이다. `us`·`global`·`eu` 를 봐도 `long` 은 전부 ✗ 다
(✓ 인 건 `short`·`chirp_2`·`chirp_3`). 즉 **"리전을 바꾸면 된다" 가 아니라 어느
리전에서도 long 계열로는 안 된다.**

**실스트림 프로브 결과 (2026-08-17) — 결론: adaptation 은 접고 `transcriptNormalization` 을 쓴다**

TTS 로 합성한 한국어 8.3초("남유다 왕국의 히스기야 왕은 여호와께 기도했습니다.
북이스라엘과 앗수르 사이에서 예루살렘을 지켜 주소서. 아멘.")를 100ms 청크로
**실시간 속도로** 흘려 비교했다.

**재현 방법** (스크립트는 세션 scratchpad 에만 있었으므로 여기 요건을 남긴다):

- TTS `v1/text:synthesize` 로 `LINEAR16`/16000Hz 합성 → **44바이트 RIFF 헤더를 벗겨**
  raw PCM 으로 만든다(마이크 경로와 같은 형태)
- `recognizer: projects/{p}/locations/{loc}/recognizers/_` 인라인 설정 —
  **클라우드 리소스를 만들지 않는다**
- 스트림은 `client._streamingRecognize()` 로 열 것. **`client.streamingRecognize()`
  는 같은 요청에 `INVALID_ARGUMENT: Invalid resource field value` 를 낸다** — 이걸
  설정 오류로 오독해 30분 날렸다. 대조군(정규화 없는 케이스)도 같이 실패하는 걸 보고서야
  설정이 아니라 스트림 생성 방식 문제라는 게 드러났다
- 오디오는 **한 번에 밀지 말고** 100ms 간격으로 나눠 쓸 것 — 통째로 보내면 측정하려는
  interim 지연이 무너진다

| 케이스 | interim | 첫 interim | "남유다" | 변경 범위 |
|---|---|---|---|---|
| A. 현행 `latest_long` | 97건 | 3149ms | ✗ **나뮤다** | — |
| B. `latest_long` + adaptation | — | — | — | **INVALID_ARGUMENT** |
| C/D. `chirp_2` + adaptation | **1건** | **6136ms** | ✓ 남유다 | 모델 교체 |
| E/F. 도쿄 `chirp_2`·`chirp_3` | — | — | — | **PERMISSION_DENIED** |
| **G. `latest_long` + `transcriptNormalization`** | **97건** | **2459ms** | **✓ 남유다** | **필드 1개** |

읽는 법:

- **`chirp_2` 는 실시간 자막에 쓸 수 없다.** adaptation 은 실제로 걸리고 "남유다" 도
  맞히지만 **interim 이 1건뿐이고 6.1초 뒤에 온다** — 발화가 끝나야 자막이 뜬다는 뜻이다.
  고유명사를 얻고 실시간성을 통째로 잃는 거래다. (덤으로 "앗수르" 는 boost 를 걸었는데도
  "아수르" 로 **더 나빠졌다** — boost 가 만능이 아니라는 증거)
- **`latest_long` + adaptation 은 조용히 무시되지 않고 명시적으로 거부된다**
  (`Config contains unsupported fields`). 잘못 넣으면 바로 터지므로 안전하다
- **도쿄 이전안(B)은 불가능하다.** Locations API 목록에는 `chirp_2`·`chirp_3` 가
  나오는데 실제로 호출하면 `PERMISSION_DENIED: ... It is no longer generally available`
  다. **"목록에 뜬다 ≠ 쓸 수 있다" 를 실측으로 확인한 사례** — 앞으로 Locations 응답만
  보고 가능하다고 판단하지 말 것
- **G 가 답이다.** interim 97건·첫 interim 2459ms 로 **현행과 동등**(오히려 약간 빠름)
  하면서 "나뮤다→남유다", "북 이스라엘→북이스라엘" 이 교정됐다. 모델·리전·recognizer
  전부 그대로고 `config` 에 `transcriptNormalization` 한 필드만 추가한다

**interim 에도 교정이 걸린다** — 별도 프로브에서 미교정 interim 4건 / 교정된 interim
47건. 문서대로 stability > 0.8 부터 적용되므로 **발화 극초반 몇 건은 교정 전 텍스트가
나간다.** 우리 퍼블리셔는 interim 델타를 송출하므로 이 구간이 자막에 잠깐 스칠 수 있다.

**채택 시 트레이드오프 (정직하게)**: 정규화는 결정론적 문자열 치환이라 **틀린 형태를
일일이 등재해야 한다**("남유다" 를 넣는 게 아니라 "나뮤다" 를 넣는다). 새 오인식이
나올 때마다 항목이 늘어난다. adaptation 은 모델을 상류에서 편향시키는 근본 처방이지만,
그 대가가 실시간성 전부라면 이쪽이 낫다.

**데이터 출처 — 한국어 원문은 이미 node 로그에 있다** (`js_pub.ts:111`
`console.log("published :", message.transcriptText)`). python 쪽은 `translated:`·
`hub: broadcast:` 둘 다 영문뿐이라(`sentenceTranslator.py:31`, `websocket.py:455`)
**python 만 보고 "원문 로깅이 없다" 고 판단하면 틀린다 — 실제로 그렇게 오판했다.**
`docker logs node | grep '^published :'` 로 수집한다.

수집 시 주의 2가지:

- **`transcriptText` 는 문장이 아니라 델타 조각이다.** `InterimChunkOrchestrator` 가
  interim 간 차분(`computeDelta`)을 큐에 쌓아 `join("")` 한 것이라, 고유명사가
  **두 published 줄에 걸쳐 쪼개질 수 있다**("나뮤" + "다"). 세그먼트 단위로 순서대로
  이어 붙여 복원한 뒤 오인식 형태를 뽑을 것
- `normalize()` 가 `.,!?` 를 제거하고 공백을 접은 뒤의 텍스트다 — 원음 그대로가 아니다

**조각화가 오히려 STT 레벨 정규화를 지지하는 근거다.** `transcriptNormalization` 은
구글이 전사문에 적용한 뒤 우리 델타 계산이 돌므로 경계 문제가 없다. 반대로 우리 코드에서
사후 치환하면 조각에 걸쳐 잘린 단어를 못 잡는다.

**watch-service tick 에는 안 보인다** — 스크립트의 node grep 패턴에
`published` 가 없다. 예배 중 원문을 보려면 tick 이 아니라 위 명령을 따로 쓸 것.

**배포하면 로그가 통째로 사라진다 (2026-08-17 실측).** 8/16 예배 원문을 회수하려
했으나 **0줄이었다** — 오늘 10:31 배포가 컨테이너를 재생성해(§5 "전 컨테이너
재생성") 이전 컨테이너의 로그가 함께 삭제됐다. `docker logs` 는 **현재 컨테이너**
것만 보여준다. 로테이션(10m×3)에 밀려 사라지는 것과는 **다른 경로**다.

→ **로그 기반 데이터는 배포 전에 회수해야 한다.** 8/19 예배 원문은 그날 예배가

`ssh ... "docker logs node 2>&1 | grep '^published :'" > 8-19-source.txt`

### 판단검증 단계 도입 (개인 설정 — 리포 밖)

질문")이 이 세션에서 반복된 오류(확인이 **가능한데** 안 하고 단정)를 덮지 못했다.

시딩임을 확인해 반박). 산출물은 `docs/session-pause-detail-{plan,judge}.md`.

### 비용 실측 — "TTS 남용이 1순위" 는 틀린 판정이었다

이 세션 중반에 `/api/mic/tts` 무인증을 1순위 비용 위험으로 올렸는데 **실측이
그걸 뒤집었다.** Cloud Monitoring 직접 조회 결과:

| | TTS | STT |
|---|---|---|
| 30일 요청 | 590건 (전부 Standard 음성) | **285,133 스트리밍 요청** |
| 무료 한도 | 월 400만 자 — 사용량 약 10% | **월 60분 오디오** |

**TTS 요금은 사실상 0 이고, 실제 비용 항목은 STT 다.** 어제 예배 44분으로 STT
무료 한도를 거의 다 쓰므로 이건 남용이 아니라 **정상 운영비**다. 백로그에서
"TTS 남용"이 아니라 **"감지 수단(예산 알림) 부재"** 로 볼 것 — 사용자 판단으로
지금은 보류(급하지 않음). 레이트 제한은 정상 사용을 안 깨는 사이징에서 비용
방어가 안 되고(5r/s×500자 = 하루 2억 자) 업링크 WS 와 경로가 겹쳐 재연결을
막을 위험이 있어 **기각**. 길이 상한과 GCP 쿼터·예산 알림이 실효 있는 수단이다.
