## 1. 배경 / 문제 정의

### 1-1. 자막 자동 스크롤이 기대대로 동작하지 않는다 (사용자 제보)

2026-08-02 사용자 제보 — prod `https://neemba.app/monitor/` 에서:
- 라이브 세션을 보는 중 새 번역이 도착해도 화면이 따라가지 않는다
- 세션 상세에 처음 들어갔을 때 맨 아래(최신)로 가지 않는다

### 1-2. 모니터 페이지를 별도 도메인으로 분리하고 싶다 — ✅ 구현 완료 (2026-08-14, PR #93·#94)

V3~V6 결정대로 배포됨: `monitor.neemba.app` 서버 블록(+SAN 확장, `--cert-name
neemba.app` 고정), 구 경로 301(깊은 경로·쿼리 보존), Cloudflare DNS-only.
본 도메인의 `/api/monitor`·`/ws/monitor` 잔류 제거만 후속으로 남음.

`neemba.app/monitor` → `monitor.neemba.app`. 운영/관측 표면을 서비스 도메인과
분리하는 일반적인 관례를 따르려는 것.

**분리로 얻는 것과 못 얻는 것을 구분해 둔다** (2026-08-02 확인):

| 기대 | 실제 |
|------|------|
| 접근 통제 경계가 도메인 단위로 깔끔해짐 | ✅ 가장 큰 실익 |
| nginx location 우선순위 다툼 해소 | ✅ 현재 `/api/monitor/` 를 `/api/` 보다 먼저 매칭시키려 신경 쓰는 비용이 사라짐 |
| 액세스 로그에서 운영자/사용자 트래픽 분리 | ✅ 스캐너 트래픽에 실사용이 묻히는 문제 완화 |
| 쿠키·자격증명 격리 | △ 현재 Basic Auth 라 쿠키 없음 |
| **장애 독립성** | ❌ **얻지 못한다.** 같은 nginx·같은 EC2 를 탄다. 앱이 죽으면 같이 죽는다 |

마지막 줄이 중요하다. "앱이 죽어도 살아 있어야 하는" 것은 **status page**
(공개용, 별 인프라·별 호스팅)의 논리다. `/monitor` 는 인증 뒤의 **internal
monitoring dashboard** 이므로 그 이점은 해당되지 않는다. 도메인 분리의 근거는
접근 통제와 라우팅 정리로 충분하며, 그 이상을 기대하면 안 된다.

**2026-08-05 실측 (prod, 주일예배 라이브 세션)**

DOM 은 `.table-wrap > table.pairs > tbody#detail-rows` 3단인데
(`index.html:51-61`), 코드는 `body.parentElement` 로 **한 단계만** 올라간다.
따라서 `wrap` 은 `<table>` 이고, `overflow:auto` 가 걸린 `.table-wrap` 이 아니다.

```js
// prod /monitor DevTools 콘솔
b.parentElement.tagName                                        // 'TABLE'
b.parentElement.scrollHeight === b.parentElement.clientHeight  // true
```

두 번째 줄이 결정적이다. 스크롤 영역이 없는 요소에 `scrollTop` 을 대입하면
브라우저가 **0 으로 클램프하고 조용히 버린다** — 예외도 콘솔 에러도 없다.
`app.ts:725`·`:774` 두 줄은 실행되지만 효과가 없다. 이것이 "코드는 있는데
안 된다" 가 오래 남아 있던 이유다.

> **검증 시 주의**: `.table-wrap.scrollTop` 의 **절대값은 증거가 못 된다.**
> 실측에서 7553 이 나왔지만 이는 사용자가 직접 휠로 내린 결과였다. 자동/수동을
> 가르려면 새 행 도착 전후로 `[scrollTop, scrollHeight - clientHeight]` 를 비교해
> **따라 올라가는지**를 봐야 한다.

**수정 방향**: `body.parentElement` → `body.closest(".table-wrap")`.
단 이 한 줄만 고치면 "위로 올려 읽는 중에도 새 번역마다 튀는" 반대 불만이
바로 생기므로, V1(바닥 판정)과 **묶어서** 낸다.

~~**반증 방법**~~ → **2026-08-05 완료.** 배포 상태부터 갈랐다: prod

### 3-2. 도메인 — DNS·인증서 현황

```
neemba.app      A → 13.125.26.93      (EC2 직결)
www.neemba.app  A → 13.125.26.93
monitor.neemba.app → 없음
NS → kara.ns.cloudflare.com / pete.ns.cloudflare.com
인증서 SAN → neemba.app, www.neemba.app        (monitor 없음)
```

**Cloudflare 는 DNS 만 하고 프록시는 꺼져 있다(회색 구름).** 근거 2가지:
A 레코드가 Cloudflare anycast(104.x·172.67.x)가 아니라 EC2 실 IP 를 반환하고,
nginx 액세스 로그에 클라이언트 실 IP 가 `$remote_addr` 로 찍힌다.

**프런트는 수정 불필요** (develop 기준):

```ts
// src/app.ts:171-172
const proto = location.protocol === "https:" ? "wss:" : "ws:";
return `${proto}//${location.host}${path}`;
```

`location.host` 기반이고 API 도 `const API = "/api/monitor"` 상대경로(`:115`)라
`monitor.neemba.app` 에서 열면 자동으로 따라간다. **단 이건 develop 코드
기준이며, prod 의 구버전 `app.js` 도 동일한지는 배포 시점에 확인해야 한다.**

## 4. 작업 단위 (WU)

### V3-A — [프런트] 자막 스크롤 UX **(release 배포 이후 착수)**

**선행**: ~~v2 release 가 prod 에 배포되어 WU4(자동 구독·gap fill)가 살아 있을 것~~
→ **충족.** 원인 조사도 2026-08-05 에 끝났다(§3-1). 바로 구현 단계다.

1. **스크롤 컨테이너 교정** — `body.parentElement` → `body.closest(".table-wrap")`.
   §3-1 확정 버그. `:725`·`:774` **두 곳 모두**. 이걸 안 고치면 아래 2~6 을
   아무리 정확히 짜도 전부 무효다(대입이 버려지므로).
2. 스크롤 상태 판정 도입 — 컨테이너가 바닥 근처인지:
   `scrollHeight - scrollTop - clientHeight <= THRESHOLD` (THRESHOLD 는 여유값,
   예: 32px. 정확히 0 비교는 소수점 스크롤·확대 배율에서 깨진다)
3. 바닥이면 기존처럼 따라가고, 아니면 스크롤하지 않는다 (V1)
4. 따라가지 않은 동안 도착한 건수를 세어 "새 번역 N건" 버튼 노출.
   클릭 시 맨 아래로 이동 + 카운터 리셋
5. 세션 상세 진입 시 맨 아래로 이동 (V2) — 초기 이력 로드 완료 **후**
6. gap fill(`:774`) 경로도 같은 판정을 타게 한다. 지금은 무조건 점프라,
   사용자가 위를 읽는 중에 재연결이 일어나면 위치를 뺏긴다

**함정**:
- **스크롤 불가 요소에 `scrollTop` 을 대입하면 예외 없이 0 으로 클램프된다.**
  §3-1 의 원인 자체다. 컨테이너를 잡을 때 `closest()` 로 명시하고, 리팩터링 중
  DOM 계층이 바뀌어도 안 깨지게 한다
- `appendChild` 직후 `scrollHeight` 는 레이아웃 확정 전 값일 수 있다.
  스크롤을 다음 프레임(`requestAnimationFrame`)으로 미루는 편이 안전하다
- 자동 스크롤이 일으킨 `scroll` 이벤트를 사용자 스크롤로 오인하면
  "따라가다 말다" 가 된다. 프로그램적 스크롤 중임을 표시하는 플래그 필요
- 세션 전환 시 카운터·플래그 리셋 (v2 의 epoch 가드 패턴 참고)

**완료 기준**: 바닥에서 수신 → 따라감 / 위로 올린 상태에서 수신 → 안 따라가고
버튼에 건수 누적 / 버튼 클릭 → 맨 아래 + 리셋 / 상세 진입 → 맨 아래 /
재연결 gap fill 중에도 위 규칙 유지.

### V3-B — [인프라] 모니터 도메인 분리 (A안) **(코드 작업 적음, 순서 중요)**

**실행 순서** — 이 순서를 지켜야 중간에 502/인증서 오류가 안 난다:

1. **Cloudflare DNS**: `monitor.neemba.app` A → `13.125.26.93`,
   **회색 구름(DNS-only) 유지** (V6)
2. **인증서 SAN 추가**: 기존 인증서를 확장한다. certbot webroot 방식 유지 —
   `-d neemba.app -d www.neemba.app -d monitor.neemba.app`.
   **DNS 전파 후에 실행할 것** (http-01 챌린지가 새 이름으로 접속해야 함)
3. **nginx**: `monitor.neemba.app` server 블록 신설, 모니터 3경로 이관.
   기존 `neemba.app` 의 `/monitor` 는 301 리다이렉트로 교체 (V4).
   `/api/monitor/` 를 `/api/` 보다 먼저 매칭시키던 주석·순서 의존은
   분리 후 불필요해지므로 정리
4. **nginx reload** 후 확인: `https://monitor.neemba.app/monitor` 200,
   Basic Auth 챌린지 동작, `/ws/monitor` 핸드셰이크 성공,
   `https://neemba.app/monitor` → 301
5. 프런트 확인 — `location.host` 기반이라 무변경 예상이나 **실제 화면에서
   WS 연결 성공을 눈으로 확인**할 것 (§3-2 단서 참조)

**함정**:
- 2번을 1번 전에 하면 챌린지 실패. **DNS 먼저**
- nginx 는 12시간마다 self-reload 로 갱신된 인증서를 집는다. 수동 배포 시엔
  `nginx -s reload` 를 직접 쳐야 즉시 반영된다
- Basic Auth htpasswd 경로(`/var/lib/neemba/secrets/monitor.htpasswd`)는
  새 server 블록에도 그대로 마운트되어야 한다 (compose 볼륨 이미 존재)

**완료 기준**: 위 4·5번 확인 항목 전부 통과 + certbot `renew --dry-run` 성공.

### 5-B. Cloudflare 프록시 전환 (B안, 후보)

프록시를 켜면 **Cloudflare Access** 로 Basic Auth 를 SSO 로 대체할 수 있다.
서브도메인 분리의 최대 실익이지만, 선행 해결 3건이 있다:

1. **WebSocket 유휴 타임아웃** — 무료 플랜 기준 100초. 현재 nginx 는
   `/ws/monitor` 에 `proxy_read_timeout 3600s` 를 주고 있어 정책이 충돌한다.

   연결 churn 이 상시화된다)
2. **클라이언트 실 IP** — `$remote_addr` 가 Cloudflare IP 가 되므로
   `CF-Connecting-IP` 처리 필요. 액세스 로그·`X-Real-IP` 전달 경로 수정
3. **SSL 모드** — Cloudflare 측이 반드시 **Full (strict)**. Flexible 이면
   nginx 의 http→https 리다이렉트와 물려 무한 리다이렉트가 난다

## 8. V3-A 브라우저 검증 (2026-08-05)

**왜 브라우저가 필요했나**: `scrollHeight`·`clientHeight` 는 렌더 결과라 jsdom 에서는
전부 0 이고, 그러면 `isAtBottom()` 이 항상 true 라 어떤 코드든 통과한다. 이 버그는
레이아웃이 있어야만 재현된다.

**하니스** (npm 의존성 0, Node 24 전역 `WebSocket`·`fetch` 로 CDP 직접 사용):
정적 파일 + API 스텁 + 최소 RFC6455 WS 서버를 띄우고, `Google Chrome.app` 을
`--headless=new` 로 붙여 `Runtime.evaluate` 로 `[scrollTop, scrollHeight-clientHeight,
배너 상태]` 를 읽는다. `/_ctl/push`(라이브 수신)·`/_ctl/drop`(강제 절단 → 재연결
gap fill)·`/_ctl/end`(session_closed) 로 상태를 만든다. 세션 scratchpad 에만 있고
리포에는 커밋하지 않았다 — 재작성이 필요하면 이 절의 설명으로 충분하다.

**결과: 19/19 통과.** 완료 기준 대응:

| 완료 기준 | 실측 |
|-----------|------|
| 바닥에서 수신 → 따라감 | `scrollTop == scrollHeight - clientHeight` 유지 |
| 위로 올린 상태 수신 → 안 따라가고 건수 누적 | `1269 → 1269` 고정, 배너 3건 → 5건 |
| 버튼 클릭 → 맨 아래 + 리셋 | 바닥 도달 + 배너 숨김 |
| 상세 진입 → 맨 아래 | 라이브(fillFrom)·종료(loadHistory) 두 경로 모두 |
| 재연결 gap fill 중에도 규칙 유지 | 바닥이면 따라가고, 위면 위치 유지 + 건수 누적 |

추가 고정: "더 보기" 는 읽던 위치 유지 / 세션 전환 시 배너 리셋 / 세션 종료 시 배너 해제 /
창 확대로 스크롤이 사라져도 배너 해제(브라우저가 `scrollTop` 클램프 시 scroll 이벤트를
발생시키므로 resize 리스너가 불필요하다).

**음성 대조군이 핵심이다.** 통과하는 테스트는 그 자체로 아무것도 증명하지 못한다 —
버그를 못 잡는 테스트도 똑같이 통과한다. 서버가 `app.js` 를 내려줄 때
`closest(".table-wrap")` 을 `parentElement` 로 되돌리게 하고 같은 스위트를 돌렸더니
**9건이 실패했고 실패 양상이 §1-1 제보와 정확히 일치했다**(`scrollTop: 0`,
`atBottom: false`, 배너 "0건" — `<table>` 은 항상 "바닥"이라 카운터가 안 돈다).
§3-1 의 원인 판정에 대한 독립적 재확인이기도 하다.

**정적 검증**: `tsc --noEmit` 무오류. 커밋된 `app.js` 가 `npm run build` 재생성물과
**바이트 일치** — 산출물을 커밋하는 D7 규약에서 이게 어긋나면 배포 코드와 소스가 갈린다.
